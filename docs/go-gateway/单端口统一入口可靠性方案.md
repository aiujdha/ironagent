# Go Gateway 单端口统一入口可靠性方案

## 1. 背景

当前 Go Gateway 已具备任务、文件、callback、fallback、runtime registry 等控制面能力，并已完成“只开放一个端口访问助手 HTTP API/UI”的最小统一入口。距离生产级 500 助手统一入口仍缺 WS/SSE 真实运行时验证、滚动摘流和压测校准。

历史测试环境或未收口部署仍可能存在多入口：

- Go Gateway：对外提供任务、文件、MCP、callback、fallback 等能力。
- IronAgent Gateway：对外提供助手原生 Web/UI/API 能力。
- Assistant Runtime：仍可能通过独立 `gateway_url` / `gateway_port` 暴露访问地址。

目标态应收敛为：

```text
外部调用方 / 浏览器 / 小熊猫 / IronAgent
  -> 一个公网入口
  -> Go Gateway / 统一入口层
  -> 按绑定、助手、任务、文件、runtime registry 路由到正确内部服务
```

性能目标按第一阶段 500 个助手 Pod 进行设计。

当前实施状态：

- 已完成 `/assistants/{assistant_id}/api/*`、`/assistants/{assistant_id}/ui/*` 与 `/assistants/{assistant_id}/ws/*` 的 Go Gateway Runtime Proxy 路径收口；真实 WS/SSE 仍需专项验证。
- 已完成 UI launch ticket -> Go Gateway signed session cookie -> Runtime UI proxy 的最小闭环。
- 已新增 `IRON_AGENT_GO_GATEWAY_PUBLIC_URL`，管理台拿到 launch ticket 后可优先生成 Go Gateway 单端口 UI 入口。
- 已新增 `prod-single-entry-nodeport` overlay，只把 Go Gateway `30808` 暴露到外部。
- Runtime Proxy 已开启长连接即时 flush、Prometheus 指标、全局并发保护、per-assistant 熔断和 self-target 防循环保护；尚未完成 WS/SSE 真实运行时专项验证。
- 文件直接上传已改为 multipart file reader 转发，直接下载和 presigned download 已走 stream；仍需部署环境并发压测确认内存曲线。

## 2. 目标

本方案目标是让 Go Gateway 或统一入口层具备以下能力：

| 目标 | 说明 |
|---|---|
| 单公网入口 | 外部只需要访问一个域名和一个端口，例如 `https://gateway.example.com` |
| 统一任务入口 | `/api/v1/chat`、`/api/v1/tasks/{task_id}`、审批、取消、fallback 查询都走同一入口 |
| 统一文件入口 | MCP 文件工具生成的 upload/download URL 也在同一入口下 |
| 统一助手入口 | 不再对外暴露每个助手 Pod 或 IronAgent Gateway 的独立端口 |
| 统一鉴权 | 小熊猫、IronAgent、浏览器、runtime heartbeat 使用不同 scope，但入口统一 |
| 统一观测 | 所有入口请求都能在 Go Gateway 聚合 metrics、audit、trace |
| 500 助手可扩展 | 能支撑 500 个助手 Pod 注册、路由、健康检测和故障隔离 |

## 3. 非目标

以下内容不作为本阶段目标：

| 非目标 | 原因 |
|---|---|
| 不让小熊猫理解 IronAgent 内部端口 | 小熊猫只应理解 IronAgent/Go Gateway 对外契约 |
| 不让 Python southbound 直接暴露公网 | Python 控制面是内部 southbound seam |
| 不把文件内容放进 MCP JSON、callback 或任务接口 | MCP 只管理文件操作，字节流走 presigned HTTP PUT/GET |
| 不用 Redis 替代 DB 权威状态 | Redis 可作为后续加速层，DB/outbox/registry 才是权威 |
| 不先做 WS/A2A 对外协议扩展 | 当前优先解决统一入口、路由可靠性和 500 Pod 基线 |

## 4. 推荐总体架构

建议采用：

```text
公网 LB / Ingress / Nginx
  -> Go Gateway Service
    -> Northbound API
    -> MCP 文件工具
    -> Callback / fallback
    -> Runtime Proxy
    -> Runtime Registry
    -> Python southbound clients
      -> admin / security-service / workspace-files / collaboration tasks
    -> Assistant Runtime Pods
```

推荐原则：

| 层级 | 职责 |
|---|---|
| 公网 LB / Ingress | TLS 终止、基础限流、转发到 Go Gateway |
| Go Gateway | 认证、授权、绑定解析、任务编排、文件管理、callback、fallback、runtime 代理 |
| Runtime Registry | 记录每个助手 runtime 的内部访问地址、健康、容量、心跳 |
| Assistant Runtime Pod | 只作为内部服务，不直接暴露公网 |
| Python 控制面 | 保持内部 southbound，不成为外部入口 |

## 5. 两种可选落地方式

### 5.1 方案 A：Go Gateway 内置 Runtime Proxy

Go Gateway 自身实现反向代理能力，把助手 UI/API/WS 请求按路径转发到对应 runtime。

示例：

```text
https://gateway.example.com/assistants/demo-main/ui/*
  -> Go Gateway
  -> Runtime Registry resolve demo-main
  -> http://ironagent-assistant-demo-main.ironagent.svc.cluster.local:18789/*
```

优点：

| 优点 | 说明 |
|---|---|
| 鉴权统一 | 所有助手访问都能复用 Gateway auth/session/ticket |
| 审计统一 | 访问日志、trace、metrics 都在 Gateway 聚合 |
| 对小熊猫透明 | 外部永远只看到 Gateway URL |
| 路由可控 | 可以按绑定、权限、runtime 健康动态路由 |
| SSRF 风险更可控 | 代理目标只允许来自 Runtime Registry |

缺点：

| 缺点 | 说明 |
|---|---|
| Gateway 复杂度上升 | 需要处理 streaming、WebSocket、header 清洗、连接池 |
| 压测要求更高 | Gateway 会成为所有助手 UI/API 流量入口 |

### 5.2 方案 B：Ingress/API Gateway 负责路径路由

Ingress 或 API Gateway 直接按 path/host 转发到不同 assistant runtime。

示例：

```text
https://gateway.example.com/assistants/demo-main/ui/*
  -> Ingress
  -> assistant-demo-main Service
```

优点：

| 优点 | 说明 |
|---|---|
| 实现快 | 主要靠 K8s Ingress 规则 |
| Gateway 压力较低 | 部分 UI/API 流量不经过 Go Gateway |

缺点：

| 缺点 | 说明 |
|---|---|
| 动态 500 助手路由维护复杂 | 需要动态生成 Ingress/Route |
| 鉴权容易分裂 | Ingress 与 Go Gateway 权限模型可能不一致 |
| 审计分散 | Gateway 不一定能看到所有请求 |
| 小熊猫契约更容易泄漏内部结构 | 路由规则与 runtime 生命周期耦合更强 |

### 5.3 推荐选择

推荐目标态采用：

```text
公网 LB / Ingress 只做 TLS 和基础转发
Go Gateway 负责统一业务入口和 Runtime Proxy
```

原因：

| 原因 | 说明 |
|---|---|
| 更符合项目边界 | Go Gateway 本来就是小熊猫与 IronAgent 的统一控制入口 |
| 更容易做鉴权和审计 | 所有外部流量统一进入 Gateway |
| 更适合后续 callback/fallback/任务状态闭环 | Gateway 能掌握任务与 runtime 的关系 |
| 更适合 500 助手动态路由 | Runtime Registry 可以直接驱动代理转发 |

## 6. 对外 URL 设计

建议所有公网能力统一挂在同一个 base URL 下：

```text
GO_GATEWAY_PUBLIC_BASE_URL=https://gateway.example.com
```

### 6.1 Northbound API

| 路径 | 用途 | 访问方 |
|---|---|---|
| `POST /api/v1/chat` | 创建任务 | 小熊猫 / IronAgent 测试端 |
| `GET /api/v1/tasks/{task_id}` | fallback 查询 | 小熊猫 / IronAgent 测试端 |
| `POST /api/v1/tasks/{task_id}/cancel` | 取消任务 | 小熊猫 / IronAgent 测试端 |
| `GET /api/v1/approvals/{approval_id}` | 查询审批 | 小熊猫 / 审批端 |
| `POST /api/v1/approvals/{approval_id}/decision` | 审批决策 | 小熊猫 / 审批端 |

### 6.2 MCP 文件入口

| 路径 | 用途 |
|---|---|
| `/mcp` | MCP JSON-RPC 管理入口 |
| `/api/v1/files/presigned/upload/{token}` | 文件上传字节流入口 |
| `/api/v1/files/presigned/download/{token}` | 文件下载字节流入口 |

原则：

```text
MCP 负责文件管理动作
presigned URL 负责文件字节流
文件内容不进入 MCP JSON
文件内容不进入 callback
文件内容不进入任务接口
```

### 6.3 助手 Runtime 入口

建议采用 path-based routing：

| 路径 | 用途 |
|---|---|
| `/assistants/{assistant_id}/ui/*` | 助手 Web UI |
| `/assistants/{assistant_id}/api/*` | 助手原生 API |
| `/assistants/{assistant_id}/ws/*` | 助手 WebSocket / SSE |

示例：

```text
https://gateway.example.com/assistants/demo-main/ui/
https://gateway.example.com/assistants/demo-main/api/v1/...
https://gateway.example.com/assistants/demo-main/ws/...
```

不建议第一阶段使用子域名：

```text
https://demo-main.gateway.example.com
```

原因是 500 个助手会带来证书、DNS、Ingress、cookie domain、跨域策略的额外复杂度。path-based routing 更适合作为第一阶段。

## 7. Runtime Registry 设计

要支撑 500 个助手 Pod，Runtime Registry 必须成为路由权威来源。

### 7.1 必要字段

| 字段 | 说明 |
|---|---|
| `assistant_id` | 助手 ID |
| `runtime_id` | runtime 实例 ID |
| `status` | `healthy` / `unhealthy` / `draining` / `stale` |
| `internal_base_url` | Gateway 访问 runtime 的内部 URL |
| `public_path_prefix` | 对外路径，例如 `/assistants/demo-main` |
| `protocols` | 支持 `http` / `ws` / `sse` |
| `capacity` | runtime 最大承载能力 |
| `in_flight` | 当前处理中请求数 |
| `active_connections` | 当前长连接数 |
| `last_heartbeat_at` | 最近心跳时间 |
| `lease_expires_at` | 心跳租约过期时间 |
| `version` | runtime 镜像或协议版本 |
| `capabilities` | runtime 能力声明 |
| `drain_mode` | 是否进入摘流状态 |

### 7.2 心跳方向

心跳必须由 runtime / IronAgent 侧主动推送到 Go Gateway：

```text
Assistant Runtime / IronAgent
  -> POST /api/v1/runtime/heartbeat
  -> Go Gateway Runtime Registry
```

不应设计成小熊猫定时请求 IronAgent 保活。

### 7.3 健康状态判断

| 状态 | 判断条件 | Gateway 行为 |
|---|---|---|
| `healthy` | 心跳未过期，容量可用 | 正常路由 |
| `at_capacity` | 心跳正常，但容量满 | 返回 429 或排队策略 |
| `draining` | runtime 主动摘流 | 不接新请求，保留已有连接 |
| `stale` | 心跳过期 | 不再路由新请求 |
| `unhealthy` | 探测失败或错误率过高 | 熔断并返回受控错误 |

## 8. 关键请求流程

### 8.1 小熊猫创建任务

```text
小熊猫
  -> POST /api/v1/chat
  -> Go Gateway 鉴权
  -> resolve user binding
  -> 创建/引用文件对象
  -> 创建 collaboration task
  -> claim
  -> start
  -> 返回 task_id + status + stage + fallback_query_url
```

返回中的 `fallback_query_url` 必须由 `GO_GATEWAY_PUBLIC_BASE_URL` 生成，不能信任任意 `X-Forwarded-Host`。

### 8.2 浏览器打开助手 UI

```text
用户 / 管理端
  -> 获取 launch ticket
  -> 打开 https://gateway.example.com/assistants/{assistant_id}/ui/?ticket=...
  -> Go Gateway 校验 ticket/session
  -> Runtime Registry resolve assistant_id
  -> 代理到内部 runtime UI
```

对外不能返回内部字段：

```text
gateway_port
pod_ip
internal_base_url
workspace_path
runtime token
```

### 8.3 助手原生 API 访问

```text
调用方
  -> /assistants/{assistant_id}/api/*
  -> Go Gateway 校验身份与助手绑定
  -> Runtime Registry resolve
  -> reverse proxy 到对应 runtime
```

### 8.4 WebSocket / SSE

如果 IronAgent UI 需要 WebSocket 或 SSE：

```text
浏览器
  -> /assistants/{assistant_id}/ws/*
  -> Go Gateway 校验 ticket/session
  -> 升级连接
  -> 代理到 runtime ws endpoint
```

必须增加：

| 控制项 | 说明 |
|---|---|
| 连接数上限 | 按全局、client、assistant 分别限制 |
| idle timeout | 防止僵尸连接 |
| drain grace | runtime 下线时允许已有连接优雅关闭 |
| reconnect hint | Gateway 返回可重连错误码或前端重连提示 |

### 8.5 MCP 文件上传下载

```text
调用方
  -> MCP ironagent.files.upload_url
  -> Go Gateway 返回 presigned upload URL
  -> 调用方 PUT 文件字节流到同一 Gateway 域名
  -> Go Gateway streaming 转发到 southbound workspace-files
```

下载同理：

```text
调用方
  -> MCP ironagent.files.download_url
  -> Go Gateway 返回 presigned download URL
  -> 调用方 GET 文件字节流
  -> Go Gateway streaming 从 southbound 读取并返回
```

必须使用流式转发，不能把大文件完整读入 Gateway 内存。

## 9. 安全设计

### 9.1 外部调用鉴权

小熊猫 / IronAgent 调用 Gateway：

```text
X-Client-ID
X-Timestamp
X-Nonce
X-Signature
X-API-Key
```

HMAC 签名串建议包含：

```text
client_id
timestamp
nonce
method
path
body_hash
```

必须做：

| 项 | 要求 |
|---|---|
| timestamp 窗口 | 防止旧请求重放 |
| nonce 去重 | 防止同窗口内重放 |
| method/path 入签 | 防止签名被换路径复用 |
| body hash 入签 | 防止 body 被篡改 |

### 9.2 浏览器访问鉴权

浏览器访问助手 UI/API 不应使用小熊猫 HMAC。

建议使用：

```text
launch ticket -> session cookie -> runtime proxy authorization
```

规则：

| 项 | 要求 |
|---|---|
| launch ticket | 短 TTL，一次性或有限次使用 |
| session cookie | HttpOnly、Secure、SameSite 合理设置 |
| assistant binding check | 用户只能访问绑定或授权的助手 |
| runtime token | 只在 Gateway 内部使用，不下发浏览器 |

### 9.3 Runtime Proxy SSRF 防护

Runtime Proxy 的上游地址只能来自 Runtime Registry，不能来自用户请求。

必须拒绝：

```text
/assistants/{assistant_id}/api?upstream=http://...
```

必须做：

| 防护项 | 要求 |
|---|---|
| assistant_id 校验 | 只允许合法 ID 字符 |
| path normalize | 防止 `../` 和双重编码绕过 |
| target allowlist | 上游必须来自 registry |
| header 清洗 | 移除 hop-by-hop headers |
| forwarded header 管控 | 不信任外部传入的 Host / X-Forwarded-* |

### 9.4 管理与调试入口隔离

管理和调试接口必须单独 scope：

| scope | 用途 |
|---|---|
| `public` | 小熊猫 / IronAgent 正式接口 |
| `admin` | 审批、配置、运维管理 |
| `runtime` | runtime heartbeat / readiness |
| `debug` | 本地或受控环境调试 |
| `proxy` | 助手 UI/API runtime proxy |

生产环境默认不开放 debug scope。

## 10. 500 助手 Pod 的可靠性设计

### 10.1 Gateway 横向扩容

建议：

```text
Go Gateway replicas >= 3
```

原因：

| 原因 | 说明 |
|---|---|
| 避免单点 | 单个 Gateway 重启不影响整体入口 |
| 分摊长连接 | 500 助手 UI/WS 可能产生大量连接 |
| 支撑滚动升级 | 至少保留可用副本 |

Gateway 不应依赖本地内存作为唯一状态源。

权威状态：

| 状态 | 权威来源 |
|---|---|
| task | DB |
| event/outbox | DB |
| runtime registry | DB 或具备一致性的 registry store |
| nonce | DB / Redis / bounded distributed cache |
| callback dead-letter | DB |

### 10.2 Runtime 心跳 TTL

建议初始参数：

| 参数 | 建议值 |
|---|---|
| heartbeat interval | 10s |
| lease ttl | 30s |
| stale threshold | 30s |
| unhealthy threshold | 连续 3 次失败 |

行为：

```text
30s 未收到心跳 -> stale
stale runtime 不接收新请求
已有长连接按 drain grace 处理
```

### 10.3 熔断与限流

按 runtime 维度做熔断：

| 条件 | 行为 |
|---|---|
| 连续连接失败 | circuit open |
| 5xx 比例过高 | circuit open |
| runtime 心跳 stale | 不再路由 |
| active_connections 达上限 | 返回 429 |

按 Gateway 维度做限流：

| 维度 | 说明 |
|---|---|
| 全局并发 | 防止 Gateway 被打满 |
| client 并发 | 防止单个调用方影响全局 |
| assistant 并发 | 防止热点助手拖垮入口 |
| 文件并发 | 防止大文件传输占满内存和带宽 |

当前 Go Gateway 已提供 `GO_GATEWAY_PROXY_MAX_IN_FLIGHT` 作为 Runtime Proxy 全局并发保护；超过阈值时返回 429。Runtime Proxy 还提供 `GO_GATEWAY_PROXY_FAILURE_THRESHOLD` 与 `GO_GATEWAY_PROXY_CIRCUIT_OPEN_DURATION`，用于在单个助手 runtime 连续 5xx 或代理失败后短期开路，避免故障 Pod 被持续打爆。

### 10.4 摘流与滚动升级

Runtime 下线流程：

```text
runtime 设置 drain_mode=true
  -> Gateway 停止新请求路由
  -> 已有 HTTP 请求继续完成
  -> 已有 WS/SSE 给 grace period
  -> 超时后关闭连接
  -> runtime Pod 退出
```

Gateway 下线流程：

```text
Gateway readiness=false
  -> LB 停止分配新流量
  -> 等待 in-flight 请求完成
  -> 等待 WS/SSE grace period
  -> 进程退出
```

### 10.5 DB 与缓存

500 助手下，不建议每个请求都强依赖多次 DB 查询。

推荐：

| 数据 | 策略 |
|---|---|
| runtime registry | DB 权威 + Gateway 本地短 TTL cache |
| binding resolve | DB/Python southbound 权威 + 30s-60s cache |
| launch ticket | 短 TTL，一次性校验后可转 session |
| nonce | 分布式去重，TTL 与 timestamp 窗口一致 |

缓存原则：

```text
缓存只能加速，不能成为唯一事实源
缓存过期或命中异常时要 fail closed
```

## 11. 性能设计

### 11.1 容量假设

第一阶段按以下基线设计：

| 指标 | 目标 |
|---|---|
| assistant runtime 数量 | 500 |
| Gateway 副本数 | 3 起步 |
| 并发浏览器会话 | 500-1500，需要压测校准 |
| 长连接数 | 500-2000，需要压测校准 |
| 单文件大小 | 按现有上限控制，必须流式转发 |
| fallback 查询 | 作为兜底，不作为主轮询压力源 |

### 11.2 Gateway 资源建议

测试环境初始建议：

| 资源 | 建议值 |
|---|---|
| replicas | 3 |
| CPU request | 1 core |
| CPU limit | 2 core |
| Memory request | 1Gi |
| Memory limit | 2Gi |

生产前必须通过压测校准。

### 11.3 连接池

Go HTTP transport 建议关注：

| 参数 | 说明 |
|---|---|
| `MaxIdleConns` | 全局空闲连接数 |
| `MaxIdleConnsPerHost` | 每个 runtime 的空闲连接数，500 host 时不能过高 |
| `MaxConnsPerHost` | 防止单个 runtime 过载 |
| `IdleConnTimeout` | 清理长期不用连接 |
| `TLSHandshakeTimeout` | 防止握手卡死 |
| `ResponseHeaderTimeout` | 防止上游无响应 |

如果 runtime 通过 ClusterIP Service 访问，host 数可能小于 Pod 数；如果直接访问 Pod IP，host 数接近 500。

### 11.4 文件传输

文件传输必须满足：

```text
上传：request.Body -> io.Pipe/multipart writer -> southbound
下载：southbound response.Body -> client response writer
```

禁止：

```text
io.ReadAll(large_file)
bytes.Buffer(full_file)
base64 file body in JSON
```

### 11.5 WebSocket / SSE

长连接会占用：

```text
file descriptor
内存
goroutine
LB connection table
```

必须设置：

| 项 | 要求 |
|---|---|
| fd limit | 节点和容器内均需足够 |
| idle timeout | 防止僵尸连接 |
| ping/pong | 检测断链 |
| per-assistant cap | 防止热点助手拖垮 Gateway |
| per-client cap | 防止单个客户端滥用 |

## 12. 观测指标

必须补齐 Prometheus metrics。

## 13. 常见故障与处理策略

| 故障 | 现象 | 处理策略 |
|---|---|---|
| runtime Pod 崩溃 | `/assistants/{id}/ui` 返回错误 | 心跳 stale，停止新路由，返回受控 503 |
| Gateway 重启 | 部分长连接断开 | 多副本 + readiness drain + 前端重连 |
| DB 不可用 | 新任务创建失败 | mutation fail closed，已有 proxy 可短 TTL cache 兜底 |
| callback 失败 | 小熊猫未收到事件 | outbox retry，失败进 dead-letter，fallback 查询可校准 |
| 文件过大 | 上传慢或失败 | MaxBytesReader + streaming + 413 |
| 热点助手过载 | 单助手延迟升高 | per-assistant cap、runtime 扩容、返回 429 |
| fallback URL 错误 | 小熊猫查询失败 | 强制配置 `GO_GATEWAY_PUBLIC_BASE_URL` |
| Host header 注入 | callback 中出现恶意域名 | 不使用外部 Host 生成 URL |
| runtime 地址被注入 | SSRF 风险 | 只允许 registry target，不接受用户 upstream |

## 14. 分阶段实施计划

### P0：冻结目标口径

目标：

```text
明确当前不是单端口统一入口
明确单端口是目标态
明确 500 助手 Pod 是容量设计基线
```

产物：

| 产物 | 说明 |
|---|---|
| 本方案文档 | 明确目标和路线 |
| 文档事实源更新 | 标注当前限制和目标态 |
| tracker 更新 | 把单端口统一入口列为后续能力 |

### P1：Runtime Proxy 最小闭环

目标：

```text
/assistants/{assistant_id}/api/*
  -> Go Gateway
  -> Runtime Registry
  -> fake runtime / real runtime
```

范围：

| 内容 | 要求 |
|---|---|
| target resolver | 只从 registry 解析 upstream |
| path rewrite | 去掉 `/assistants/{id}/api` 前缀后转发 |
| HTTP proxy | 支持 GET/POST/PUT/DELETE |
| header 清洗 | 移除 hop-by-hop headers |
| 超时 | dial/read/write timeout |
| 测试 | httptest fake runtime |

暂不做：

```text
WebSocket
自动扩缩容
```

### P2：浏览器 UI 入口

目标：

```text
/assistants/{assistant_id}/ui/*
  -> Go Gateway
  -> runtime UI
```

范围：

| 内容 | 要求 |
|---|---|
| launch URL | 对外只返回 Gateway public URL |
| ticket/session | 验证用户是否能访问助手 |
| cookie/path | 保证 path-based UI 能正常工作 |
| 静态资源 | 正确代理 js/css/assets |

### P3：WebSocket / SSE

目标：

```text
/assistants/{assistant_id}/ws/*
  -> Go Gateway
  -> runtime ws/sse
```

范围：

| 内容 | 要求 |
|---|---|
| upgrade tunnel | 支持 WebSocket |
| connection cap | 全局、client、assistant |
| idle timeout | 防僵尸连接 |
| graceful drain | runtime/Gateway 下线可控 |

### P4：可靠性加固

目标：

```text
500 assistant registry + runtime proxy 可以稳定运行
```

范围：

| 内容 | 要求 |
|---|---|
| circuit breaker | 按 runtime 熔断 |
| bulkhead | 按 assistant 隔离 |
| backpressure | 429/503 受控返回 |
| metrics | Prometheus 指标 |
| audit | 入口与 proxy 审计 |

### P5：K8s 收口

目标：

```text
只暴露 Go Gateway / Ingress 一个公网入口
ironagent-gateway 和 runtime services 改为内部访问
```

范围：

| 内容 | 要求 |
|---|---|
| Service | runtime 只保留 ClusterIP |
| NodePort | 关闭 30789/30790 对外暴露 |
| Ingress | 只转发到 Go Gateway |
| ConfigMap | 统一 `GO_GATEWAY_PUBLIC_BASE_URL` |
| Secret | 不使用占位值 |

### P6：500 助手压测

目标：

```text
证明 Gateway 在 500 runtime registry 下路由、文件、callback、fallback 稳定
```

测试项：

| 测试 | 目标 |
|---|---|
| 500 registry seed | Gateway 能加载和查询 |
| 500 UI session | 验证 proxy 连接稳定 |
| 1000 fallback query | 验证 fallback 不拖垮 DB |
| 50MB 文件并发 | 验证 streaming 不爆内存 |
| runtime 摘流 | 验证 draining |
| Gateway 滚动升级 | 验证可用性 |

## 16. 验收标准

单端口统一入口达到可验收状态时，必须满足：

| 标准 | 验收方式 |
|---|---|
| 外部只开放一个公网入口 | K8s Service/Ingress 检查 |
| 小熊猫任务接口可用 | `/api/v1/chat` 全流程测试 |
| fallback URL 使用同一公网入口 | callback payload 检查 |
| MCP upload/download URL 使用同一公网入口 | MCP 工具返回值检查 |
| 助手 UI 使用同一公网入口 | 浏览器打开 `/assistants/{id}/ui` |
| 助手 API 使用同一公网入口 | curl `/assistants/{id}/api/...` |
| 不暴露内部 runtime 地址 | 响应体和前端配置检查 |
| 500 runtime 可注册 | registry seed / heartbeat 测试 |
| stale runtime 不接新请求 | 健康状态测试 |
| Gateway 滚动升级不中断整体服务 | K8s rollout 测试 |
| 文件传输不爆内存 | 并发上传下载压测 |

## 17. 当前必须确认的问题

| 问题 | 影响 |
|---|---|
| 最终单端口由 Go Gateway 代理，还是由 Ingress/API Gateway 代理 | 决定开发范围和安全边界 |
| 助手 UI 是否依赖 WebSocket/SSE | 决定 P3 是否必须前置 |
| IronAgent UI 是否支持 path prefix 部署 | 决定是否需要前端 base path 适配 |
| 500 Pod 的真实并发模型 | 决定 Gateway 资源与压测指标 |
| runtime 是 Pod IP、Service per assistant，还是统一 Service + path | 决定 registry target 结构 |
| 浏览器访问助手用 launch ticket 还是统一登录 session | 决定 UI 鉴权方案 |

## 18. 推荐下一步

建议按以下顺序推进：

```text
1. 确认采用 Go Gateway Runtime Proxy 作为目标态
2. 先实现 /assistants/{assistant_id}/api/* 的 HTTP proxy 最小闭环
3. 用 fake runtime + 真实 Runtime Registry 做路由测试
4. 再接 /assistants/{assistant_id}/ui/* 和 launch ticket
5. 最后补 WebSocket/SSE、熔断、限流、压测
```

不建议直接做：

```text
1. 直接关闭 30789/30790
2. 直接让小熊猫访问 IronAgent Gateway
3. 直接为 500 个助手生成 500 条公网 Ingress
4. 在没有 registry 权威状态前横向扩容多 Gateway
5. 在文件仍非 streaming 时做大并发文件压测
```

最终路线：

```text
先让 Go Gateway 掌握 runtime 路由权威；
再让所有外部入口收敛到 Go Gateway；
最后用 500 助手压测验证可靠性和容量边界。
```
