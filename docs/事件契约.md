# Go Gateway 事件契约

本文档只描述 callback 事件。接口字段见 `接口契约.md`，状态机见 `状态机.md`。

## 1. Callback 主路径

Go Gateway 在任务状态变化时向上游 `callback_url` 投递事件。

callback 必须满足：

- URL host 命中 allowlist。
- 生产默认拒绝 localhost、私网和 link-local 地址。
- Gateway 主动 POST 推送任务状态、过程和结果。
- Gateway 不要求上游返回业务 ACK；HTTP 2xx 且响应 body 未显式拒收即视为本次推送成功（见「推送结果判定」）。
- Gateway 失败后记录失败原因并 retry，超过上限进入 dead-letter。
- 上游长时间未收到 callback 时，通过 `GET /api/v1/tasks/{task_id}` 做 fallback 查询。

## 2. Callback Header

Callback 业务契约以 body 为准。当前实现可能附带以下观测和兼容 header，便于 Gateway 内部日志、排查和兼容旧测试工具；上游不需要依赖、保存或回传这些 header。

```http
X-IronAgent-Event-ID: <event_id>
X-IronAgent-Event-Seq: <event_seq>
X-IronAgent-Event-Type: <event_type>
X-IronAgent-Timestamp: <rfc3339_nano>
X-IronAgent-Nonce: <nonce>
X-IronAgent-Signature: <hex_hmac_sha256>
Content-Type: application/json
```

不存在 client_id 相关 header。

## 3. Callback Body

通用字段：

| 字段 | 说明 |
| --- | --- |
| `taskId` | Gateway 对外任务 ID。 |
| `status` | 统一外部状态。 |
| `stage` | 统一外部阶段。 |
| `eventId` | 事件唯一标识。 |
| `eventSeq` | 同一任务内单调递增的事件序号。 |
| `eventType` | 事件类型，见「事件类型」。 |
| `timestamp` | 事件时间戳，RFC3339Nano。 |
| `nonce` | 签名用随机数。 |
| `signature` | HMAC-SHA256 签名，hex。 |
| `replyText` | 过程进度或最终结果文本；过程类 callback 使用 Markdown 片段。 |
| `files` | 结果文件引用，仅完成时可有。 |
| `files[].fileId` | 文件唯一标识。 |
| `files[].fileName` | 文件名。 |
| `files[].size` | 文件大小，单位字节，字符串。 |
| `files[].mimeType` | 文件 MIME 类型。 |
| `files[].download_url` | 文件下载地址。 |
| `errorCode` | 失败错误码，仅失败时有值。 |
| `errorMessage` | 失败原因，仅失败时有值。 |
| `errorLocation` | 失败位置，仅失败时有值。 |
| `errorReason` | 失败详细原因，仅失败时有值。 |

禁止字段：

- `claim_token`
- `input_object_id`
- `workspace_file_id`
- Python southbound URL
- 文件字节或 base64

## 4. 事件类型

| 事件 | 触发条件 | 典型状态/阶段 |
| --- | --- | --- |
| `task.accepted` | Gateway 接收任务并完成初始入库或编排。 | `processing/queued` |
| `task.progress` | 任务推进到执行、工具、上传、下载等阶段。 | `processing/thinking`、`processing/tool_running` |
| `chat.progress` | runtime 上报助手思考、规划或普通 chat 过程进度。 | `processing/tool_running` |
| `delta` | runtime 上报可合并的助手增量文本。 | `processing/tool_running` |
| `tool.progress` | runtime 上报工具通用过程进度。 | `processing/tool_running` |
| `tool.exec` | runtime 上报工具执行、调用或运行开始。 | `processing/tool_running` |
| `tool.output` | runtime 上报工具输出、读取、写入或结果内容；过长内容会截断。 | `processing/tool_running` |
| `tool.process` | runtime 上报工具处理过程。 | `processing/tool_running` |
| `file.generated` | runtime 上报结果文件已生成或写入。 | `processing/tool_running` |
| `skill.started` | runtime 上报 skill 启动。 | `processing/tool_running` |
| `skill.completed` | runtime 上报 skill 完成。 | `processing/tool_running` |
| `task.approval_required` | southbound 进入审批等待。 | `pending_approval/waiting_approval` |
| `task.approval_resolved` | 审批被允许或拒绝。 | `processing/tool_running` 或 `rejected/blocked` |
| `task.retrying` | 队列 attempt 失败，任务进入重试等待。 | `retrying/retry_wait` |
| `task.completed` | 任务成功完成。 | `completed/done` |
| `task.failed` | 任务失败。 | `failed/error` |
| `task.cancelled` | 用户或系统取消任务。 | `cancelled/blocked` |
| `task.rejected` | 审批拒绝或策略拒绝。 | `rejected/blocked` |

说明：

- 任务超时（`timeout`）状态变化当前不触发任何 callback 事件；上游只能通过 fallback 查询发现超时。
- 同一任务尚未投递的 `task.retrying` 事件会被后续新事件（新的 `task.retrying`、`task.completed`、`task.failed`、`task.cancelled`、`task.rejected`）supersede 合并，上游不应假设能收到每一次重试通知。

## 5. 推送结果判定

上游不需要返回 ACK body。默认情况下 Gateway 判断 HTTP 推送结果，并解析 2xx 响应 body 中的显式 ack 字段：

| 结果 | Gateway 处理 |
| --- | --- |
| HTTP 2xx，且 body 未显式拒收 | 记录推送成功。 |
| HTTP 2xx，但 body 为 JSON 且 `ok`/`success`/`received`/`handled`/`accepted` 任一字段为假值 | 判定 `ack_rejected`，按 retry 策略重试。 |
| 接口无法连通、DNS 错误、连接拒绝、超时 | 记录失败原因并按 retry 策略重试。 |
| HTTP 4xx/5xx | 记录状态码和响应体摘要，并按 retry/dead-letter 策略处理。 |

上游也可通过 `POST /api/v1/webhooks/ack` 按 `event_id`/`task_id` 主动回报 ACK；该端点仅用于 ACK 对账记录，不参与上述推送结果判定。

生产默认应使用 `callback_accept_any_response=false`。Gateway 会在发出 callback 后读取上游 HTTP 响应并记录
`callback_response_status_code`、`callback_response_body` 等字段；只有 HTTP 2xx 且未被 body 显式拒收记录为 `delivered`，
HTTP 4xx/5xx、`ack_rejected` 或连接失败、DNS 错误、连接拒绝、超时等错误按 retry/dead-letter 策略处理。
`callback_accept_any_response=true` 仅作为临时兼容模式使用，启用后只要观察到 HTTP 响应就记录为
`delivered`，但日志和投递记录必须标注兼容模式。

日志需要包含推送时间、`taskId`、callback host、尝试次数、失败分类、HTTP 状态码和失败详情。上游是否真实消费成功由上游自行保证；如上游未收到事件，应以 fallback 查询为准。

## 6. Retry 与 dead-letter

投递失败处理：

- 5xx、网络错误、超时：进入 retry。
- 4xx：默认同样进入 retry；仅当 4xx（408/425/429 除外）且响应 body 含接收端限流文案 `exceed max call times` / `exceeded max call times` 时，视为接收端永久拒收，立即停止重试并进入 dead-letter。
- 408/425/429：始终按可恢复错误重试。
- 超过最大尝试次数：进入 dead-letter。

retry 要求：

- 指数退避。
- jitter。
- 租约 claim，避免多 worker 重复投递。
- 事件幂等。

dead-letter 要求：

- 可查询。
- 可人工 replay。
- replay 不改变原始事件语义。

## 7. 顺序与幂等

上游应按 `taskId` 做幂等和状态校准。

同一 `task_id` 下：

- `eventSeq` 单调递增。
- 上游遇到乱序事件时，应以 fallback 查询结果作为补偿。
- callback 不承诺替代最终状态查询。
