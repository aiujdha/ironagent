## 背景

能力策略会影响助手容器能使用哪些工具。当前后台策略修改与运行中容器的真实生效状态之间存在不确定性，需要先定义清楚产品行为，再实现或调整代码。

Runtime observed state、freshness、多节点 Gateway registry、SSE/fallback 降级、saved config 与 applied runtime generation/hash 的通用状态模型由 `specs/runtime-260518-1025/` 管理。本 spec 只保留能力策略生效规则。

## 摘要

管理员需要清楚知道：能力策略修改后，会如何影响已经存在的助手容器。第一版明确采用“重启后生效”，不对运行中容器宣称热生效。

## 问题

能力策略决定助手可以使用哪些工具，以及哪些工具需要审批。当前管理员可以编辑策略，但不清楚运行中的助手容器是否会立即使用新策略。这会造成安全上的误解：后台页面看起来已经更新，但 runtime 可能仍按旧上下文执行。

## 参与方

- 管理员：编辑能力策略，并需要看到明确的生效状态。
- 助手 runtime：在助手容器内执行工具权限策略。
- Security Service：第一版参与审批和审计，不作为能力策略的最终集中拦截点。
- Go Gateway：可能负责请求路由或策略应用相关控制动作。
- Workspace：可能包含已安装的 skills/plugins，这些内容可能暴露工具能力。
- 终端用户：和受策略影响的助手交互。

## 生效时机

- 第一版明确采用“重启后生效”。
- 未运行的助手在下次启动时使用最新已保存策略。
- 如果未来实现热更新，必须向管理员展示热更新是否成功。
- 如果策略仅保存但 runtime 未生效，admin 页面必须明确展示“需重启”或等价状态。

## 权限与安全边界

- 只有授权管理员可以编辑能力策略。
- 只有授权管理员可以触发受影响助手的重启或策略应用动作。
- 普通终端用户不能直接修改能力策略。
- 策略编辑、重启、重新加载和失败路径都需要审计。
- 第一版不要求 Security Service 成为所有工具调用的最终安全闸门。

## 非目标

- 本 spec 不要求所有策略修改都必须实现真正热更新。
- 本 spec 不重设计整个权限模型。
- 本 spec 不修改 skill/plugin 包格式。
- 本 spec 不新增管理员权限。
- 本 spec 不实现 Security Service 集中拦截；如后续需要，单独开 S3 spec。

## 行为

B1. 当管理员编辑能力策略时，系统必须明确展示生效范围：运行中容器需要重启后生效，未运行助手下次启动生效。

B2. 当助手未运行时，下次启动必须使用该助手对应的最新已保存能力策略。

B3. 当助手已经运行且不支持热更新时，admin 页面不能暗示运行中的容器已经采用了新策略。

B4. 当助手已经运行且策略发生变化时，系统必须能识别哪些助手受到该策略影响。

B5. 当需要重启后生效时，管理员必须看到明确的操作入口或说明，用于重启受影响的助手容器。

B6. 当助手有正在执行的任务时，系统必须等待当前任务完成后再重启，不立即中断活跃任务。

B7. 当策略移除了原本允许的危险工具后，在文档定义的生效点之后，runtime 不能继续允许该工具。

B8. 当策略变化影响已安装 skills/plugins 提供的工具时，系统必须定义这些 runtime 工具列表是否需要重新加载、重启或重新安装。

B9. 当策略重新加载或容器重启失败时，管理员必须看到失败状态；没有证据时，不能报告助手已经使用新策略。

B10. 系统必须记录策略编辑，以及用于应用策略的重启/重新加载动作审计。
