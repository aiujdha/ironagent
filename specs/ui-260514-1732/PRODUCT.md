## 背景

当前 WebUI 会把待审批项展示在聊天页工作台侧栏里。用户审批需要从侧栏转为聊天页弹窗，由用户直接判断允许或拒绝；系统/管理员审批仍然走管理后台审批。

## 摘要

问题：聊天过程中出现需要用户判断的审批时，侧栏展示不够直接，用户容易漏掉当前必须处理的允许/拒绝决策。

期望结果：当当前聊天上下文出现待用户处理的审批时，WebUI 以弹窗形式阻塞展示审批内容，并让用户在弹窗里选择“允许”或“拒绝”。

## 问题

- 待审批项目前是工作台侧栏内容，不是主流程弹窗。
- 系统/管理员审批应继续由管理后台处理，不进入聊天页用户审批弹窗。
- 侧栏审批区不再作为审批入口保留。

## 参与方

- 终端用户：在 WebUI 聊天页看到审批弹窗，并选择允许或拒绝。
- Admin：继续在管理后台处理系统/管理员审批。
- Security Service：继续作为审批列表和审批决策的后端来源。
- UI：负责把当前用户审批从侧栏主决策入口改为弹窗主决策入口。

## 生效时机

- 发布后生效：用户刷新或重新打开 WebUI 后看到新的审批交互。

## 权限与安全边界

- 本次不新增可审批对象，不放宽谁可以审批。
- 本次不修改审批 API、鉴权 Header、审计语义或超时策略。
- 如果当前页面没有处理审批所需的凭证，弹窗必须展示失败或不可处理状态，不能伪造成功。

## 非目标

- 本 spec 不修改 Security Service 审批决策接口。
- 本 spec 不修改审批状态机、审计、超时和自动拒绝规则。
- 本 spec 不把系统/管理员审批搬进 WebUI 聊天弹窗。
- 本 spec 不移除管理台审批能力。
- 本 spec 不做部署、镜像或线上发布。

## 行为

B1. 当当前聊天上下文存在待用户处理的审批时，WebUI 必须以弹窗形式展示审批内容。

B2. 用户审批弹窗必须提供“允许”和“拒绝”两个明确动作。

B3. 当用户在弹窗选择允许或拒绝后，WebUI 必须调用现有审批决策路径，并在成功后关闭该审批弹窗。

B4. 当审批决策失败时，弹窗必须保留当前审批并展示失败反馈，不能把审批从待处理队列中移除。

B5. 当同时存在多个待用户处理的审批项时，WebUI 一次只要求用户处理一个当前审批；处理完当前条后自动显示下一条。

B6. 当待审批项不属于当前聊天助手或会话时，WebUI 不应在当前聊天页弹出该审批。

B7. 当没有待用户处理的审批项时，WebUI 不显示审批弹窗。

B8. 系统/管理员审批不得进入聊天页用户审批弹窗，仍然通过管理后台处理。

B9. 侧边栏不再保留审批区或审批操作入口。

B10. 本次变更不得修改后端审批接口、权限判断或审计落点。
