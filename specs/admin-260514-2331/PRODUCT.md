## 背景

后台管理需要覆盖用户、助手、工作区文件、skill/plugin 能力装配、审计日志和助手运行状态。项目主要面向内网环境，但本次公开业务 API 明确要求可用 `curl` 调用，并且要满足用户提供的 `docs/archive/historical/IronAgent-API接口契约-curl复测报告-2026-05-08.md`（已归档）中的接口契约。

内网浏览器安全策略严格，浏览器端不能依赖缓存 `token`、`key`、`ticket`，也不能要求页面长期持有这些凭据。后台页面必须使用服务端会话或 `HttpOnly Cookie` 等方式承载管理态，不能把 admin/runtime 凭据暴露给浏览器脚本。

Runtime 状态一致性、freshness、多节点 Gateway registry 和 Admin SSE/fallback 的详细规则由 `specs/runtime-260518-1025/` 管理。本 spec 的 B7、B8、B9、B11、B30、B34、B35 只保留后台管理闭环口径，不代表新的 runtime-state spec 已 verified。

## 摘要

问题：当前后台管理、公开 API、助手 runtime、workspace、能力市场和审计行为没有统一成一个可验收闭环。期望结果：先形成完整 S3 规格，后续实现时按规格逐项落地，并用本地测试、代码审计、API 响应、页面截图、容器状态、workspace 文件树和审计记录闭环。

## 问题

- 公开业务 API 需要按既有合同支持 `curl`，但本次确认首期允许公网无 token/签名访问，风险必须显式记录。
- 管理后台需要支持用户、助手、状态实时展示、生命周期操作、工作区文件、能力装配和审计日志，但首期不能把管理 token 存进浏览器。
- 助手容器运行在内网，定位为轻量办公助手，必须具备 Python 办公文档处理和图表能力。
- 工作区文件在后台管理、助手容器侧栏、公开 API、runtime 之间必须有清晰的权限、目录和刷新语义。
- skill/plugin 必须从市场选择版本装配到单个助手，安装、启用、禁用、卸载后必须能反映 runtime 生效状态。
- 审计日志需要覆盖高风险操作、失败请求、审批、控制会话和能力 reload，但健康检查纠偏不进入正式审计日志。

## 参与方

- 超级管理员：使用后台页面管理用户、助手、工作区文件、skill/plugin 能力、审计日志和助手生命周期。
- API 调用方：通过 `curl` 或系统集成调用公开业务 API。
- 终端用户：通过上游系统间接使用已绑定助手。
- 助手 runtime：运行具体助手容器，执行聊天、文件分析、Python 办公处理和图表生成。
- Workspace：承载每个助手的 `temp`、`persistent`、`skills`、`plugins` 目录。
- Skill/plugin：从市场提供能力包，装配到指定助手并通过 runtime reload 生效。
- 内部服务：负责用户与助手绑定、状态同步、工作区刷新、市场查询、审计写入、callback 投递和控制会话。

## 生效时机

- 后台会话：管理员登录或从后台入口进入后立即生效；会话过期后自动跳转登录页，登录成功后回到原页面。
- 公开业务 API：发布后立即按契约生效。
- 助手创建：必须先创建用户，再创建助手；创建助手时绑定已存在的 `user_id` 后生效。
- 助手状态：页面优先通过 SSE/WebSocket 状态快照刷新；断开后自动降级为 3-5 秒轮询，freshness 与降级语义以 `specs/runtime-260518-1025/` 为准。
- 助手生命周期：启动立即触发；停止、重启、删除需要二次确认后触发。
- 工作区文件：后台或助手侧栏上传成功后，必须触发对应助手 workspace refresh/reload。
- 能力装配：安装、升级、卸载、启用、禁用后自动触发 runtime reload；reload 成功后运行态可用。
- Python 镜像依赖：新镜像发布后生效。

## 权限与安全边界

- 后台管理员首期只有超级管理员一种角色，拥有全部后台操作权限。
- 后台页面首期沿用现有登录方式，只补齐最小可行的 `HttpOnly Cookie` 会话和过期重进流程。
- 浏览器脚本不得读取、保存或发送内部服务凭证、gateway token、runtime token、API key 或长期 ticket。
- 首期不提供管理后台关键操作的 `curl` 契约；管理操作通过后台页面或后端内部接口完成。
- 公开业务 API 首期按复测报告，不要求 `X-API-Key`、`X-Client-ID`、`X-Timestamp`、`X-Nonce`、`X-Signature`、Bearer token 或 Cookie。
- 公开业务 API 首期允许公网访问，且不做限流；这是 S3 高风险边界，必须写入风险和后续补强计划。
- 公开业务 API 使用的所有外部可见 ID 必须是高熵随机 ID，至少包括 `file_id`、`task_id`、`approval_id`。
- 公开业务 API 中带 `user_id` 的接口必须校验 `user_id` 已存在，并校验文件、任务、助手归属。
- 审批详情和审批决策接口按复测报告开放，首期不额外要求 `user_id`、token 或签名。
- 所有公开业务 API 失败请求必须进入正式审计日志。

## 非目标

- 本 spec 不实现代码；实现前必须先完成 review，并将状态改为 `ready`。
- 本 spec 不做管理后台 `curl` 契约。
- 本 spec 不做后台角色细分，首期只有超级管理员。
- 本 spec 不做市场上传/发布能力；首期假设市场或类 SkillHub 服务中已经存在可选能力。
- 本 spec 不做多助手绑定；首期一个用户只有一个默认助手，但保留未来多助手口径。
- 本 spec 不做多助手批量安装、卸载、启用、禁用或 reload。
- 本 spec 不做公开业务 API token、签名或限流。
- 本 spec 不做独立回滚按钮；能力降级通过重新选择旧版本安装覆盖实现。
- 本 spec 不触碰真实环境；首轮验收只做本地代码级测试、代码审计和测试计划。

## 行为

B1. 当管理员创建用户时，系统必须创建可被后续助手绑定的后台用户记录。

B2. 当管理员创建助手时，必须传入已存在的 `user_id`；如果 `user_id` 不存在，必须返回明确错误，不得自动创建用户。

B3. 当用户已绑定默认助手时，公开业务 API 只传 `user_id`，系统自动路由到该用户的默认助手。

B4. 当未来需要一个用户绑定多个助手时，系统必须保留“默认助手”概念；首期公开业务 API 不接受也不要求 `assistant_id`。

B5. 当助手被删除时，系统必须软删除助手并禁用运行态；用户、审计日志、历史任务和工作区文件保留。

B6. 当用户的默认助手已软删除或无可用助手时，公开业务 API 必须返回明确错误，要求后台重新创建助手后才能继续调用。

B7. 当后台助理列表展示助手时，必须展示 `running`、`stopped`、`starting`、`stopping`、`restarting`、`failed` 之一及最后更新时间。

B8. 当后台助理详情展示助手时，必须包含能力配置、容器名称、工作目录和能力 readiness；这些字段不放在列表页。

B9. 当后台助理页面打开时，助手状态必须优先使用 SSE/WebSocket 推送；连接断开后自动降级为 3-5 秒轮询。

B10. 当管理员启动助手时，不需要二次确认；当管理员停止、重启或删除助手时，必须二次确认。

B11. 当后台数据库状态与容器真实状态不一致时，后台健康检查每 10 秒检测并回写数据库状态；该纠偏写系统事件日志或运行日志，不进入正式审计日志。

B12. 当管理员人工启动、停止、重启或删除助手时，正式审计日志必须记录状态变更操作。

B13. 当公开业务 API 被 `curl` 调用时，首期只覆盖 `health`、`files`、`chat`、`tasks`、`approvals`；管理后台关键操作不提供 `curl` 契约。

B14. 当调用 `GET /api/v1/health` 时，不需要鉴权，返回字段必须满足复测报告中的健康检查契约。

B15. 当调用 `POST /api/v1/files/upload` 时，只接受 multipart 表单字段 `user_id` 和 `file`；文档外字段如 `assistant_id` 必须返回 400。

B16. 当上传文件成功时，文件必须落到该 `user_id` 默认助手的 workspace `temp/` 目录，并返回 `file_id`、`filename`、`size`、`mime_type`、`created_at`。

B17. 当调用 `GET /api/v1/files/{file_id}?user_id=...` 时，必须校验文件归属并返回文件元信息；错误 `user_id` 返回 403，缺少 `user_id` 返回 400。

B18. 当调用 `GET /api/v1/files/{file_id}/download?user_id=...` 时，必须校验文件归属并返回文件二进制内容；浏览器或上游不得直接访问 workspace 路径。

B19. 当调用 `POST /api/v1/chat` 时，请求体只允许契约字段 `request_id`、`user_id`、`conversation_id`、`message`、`files`；缺少 `request_id` 返回 400，未知 `file_id` 在创建任务前返回 422，文档外字段如 `assistant_id` 返回 400。

B20. 当任务创建成功时，系统必须立即返回接收回执，并异步执行任务；`GET /api/v1/tasks/{task_id}` 必须返回与 callback 业务字段一致的兜底结果。

B21. 当调用 `POST /api/v1/tasks/{task_id}/cancel` 时，执行中任务可取消；终态任务必须返回 409。

B22. 当任务状态变化时，Gateway 必须主动 POST callback；上游 HTTP 2xx 即视为成功，不要求 ACK body，失败时记录重试和 dead-letter 日志。

B23. 当调用 `GET /api/v1/approvals/{approval_id}` 或 `POST /api/v1/approvals/{approval_id}/decision` 时，首期按复测报告开放，不额外要求 `user_id`、token 或签名；非法 decision 返回 400。

B24. 当公开业务 API 暴露 `file_id`、`task_id`、`approval_id` 时，这些 ID 必须是高熵随机 ID，不得使用自增、短号或可枚举 ID。

B25. 当公开业务 API 请求失败时，全部失败请求必须进入正式审计日志。

B26. 当后台管理员查看工作区文件时，可以查看并下载任意助手的 `temp`、`persistent`、`skills`、`plugins` 目录文件。

B27. 当助手容器侧栏查看工作区文件时，只能查看并下载当前助手自己的 `temp`、`persistent`、`skills`、`plugins` 目录文件。

B28. 当后台管理员上传工作区文件时，只能向任意助手的 `temp` 或 `persistent` 上传；当助手侧栏上传文件时，只能向当前助手自己的 `temp` 或 `persistent` 上传。

B29. 当用户在文件视图进入 `skills` 或 `plugins` 目录时，该目录只读；不能通过文件视图上传、删除或覆盖能力包。

B30. 当后台或助手侧栏上传文件成功后，系统必须触发对应助手 workspace refresh/reload。

B31. 当管理员在助理页面添加能力时，必须从市场或类 SkillHub 服务选择 `skill/plugin` 和具体版本；助理页面不直接上传安装包，市场上传/发布不属于本次范围。

B32. 当能力安装到助手时，该能力版本必须固定；已安装能力不自动升级，管理员必须手动选择新版本并确认升级。

B33. 当管理员需要恢复旧能力版本时，首期不提供独立回滚按钮；管理员重新选择旧版本安装覆盖。

B34. 当管理员安装、升级、卸载、启用或禁用 `skill/plugin` 时，只作用于当前选中的单个助手，不支持多助手批量操作，并自动触发 runtime reload。

B35. 当能力配置写入成功但 runtime reload 失败时，页面必须展示“安装成功但运行态未生效”或等价状态，审计日志必须记录操作者、助手、能力 id、版本、动作、结果、错误码和错误信息。

B36. 当后台审计日志页面打开时，必须支持列表查询、筛选和导出 CSV/JSON；筛选条件至少包含时间、用户、助手、操作类型、结果、错误码。

B37. 当审计日志写入后，默认保存 45 天，超过后允许归档或清理。

B38. 当后台控制会话创建、消费、过期或拒绝时，必须进入正式审计日志；页面会话过期后自动跳转登录页重新登录，登录成功后回到原页面。

B39. 当构建助手 Python 镜像时，必须内置办公处理和图表依赖：`numpy==1.26.4`、`openpyxl==3.1.5`、`python-docx==1.1.2`、`matplotlib==3.8.4`、`pandas>=2.1.0`、`python-pptx`、`pypdf`、`pdfplumber`、`reportlab`、`Pillow`、`tabulate`，并通过 apt 安装 `fonts-wqy-zenhei`。

B40. 当本 spec 后续进入实现时，首轮验收只做本地代码级验证；不得触碰真实环境或改变线上暴露边界，除非另开确认。
