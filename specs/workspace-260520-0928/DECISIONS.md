## D1. 展示数据源必须是 DB-only 索引

**决策**

管理后台的工作区文件展示、助手工作区摘要、助手已安装能力展示，默认数据源必须是数据库索引。页面 GET 查询只能做只读 DB 查询、权限过滤、筛选、排序、分页和状态展示。

**必须满足**

- 工作区文件展示读取 `workspace_files` 或等价 DB 索引。
- 能力安装展示在 Phase 2 后读取能力安装索引和必要的 `workspace_files` 聚合。
- 查询结果必须分页；默认 `page_size` 不超过 50，最大 `page_size` 不超过 200，超过 200 必须返回 400。
- GET 查询路径的 COS list 次数必须为 0。
- GET 查询路径的本地 workspace 递归扫描次数必须为 0。
- GET 查询路径的全助手 fan-out 同步次数必须为 0。

**明确拒绝**

- 页面 GET 查询实时扫描所有助手 workspace。
- 页面 GET 查询实时 list COS。
- 页面 GET 查询调用 legacy hydrate。
- 页面 GET 查询复用会产生副作用的 `WorkspaceFileService.list_files()`。
- 以“先查 COS、失败再查 DB”作为后台展示默认路径。
- 以本地目录位置实时推断后台展示事实。

**理由**

500-2000 个助手规模下，展示路径不能绑定文件系统、COS、助手数量和同步副作用。DB-only 索引是唯一可分页、可授权、可压测、可观测的默认展示事实源。

**验收口径**

只要 GET 查询仍能触发 COS list、workspace scan、legacy hydrate 或全助手 fan-out，同步迁移就不得标记为完成。

## D2. 所有刷新和校验必须是 job/status 语义

**决策**

所有会改变索引状态的刷新、导入、校验和修复动作，都必须通过显式同步任务表达。页面查询和任务创建必须分离。

**必须满足**

- 刷新当前助手必须创建或复用单助手 job，并立即返回 `job_id`、`status` 和当前旧索引状态。
- 刷新全部助手必须创建批量 job，并受限排队或分片执行。
- COS 导入必须创建 `cos_import` job。
- 缺失校验和修复必须创建 `reconcile` job。
- job 至少具备 `pending`、`running`、`succeeded`、`failed`、`cancelled` 或等价状态。
- job 必须记录 scope、mode、操作者、开始/结束时间、扫描数、更新数和错误。
- 同一 scope/mode 的重复点击必须具备幂等或去重机制，不能无限创建 running job。

**明确拒绝**

- 切换页面隐式触发同步。
- 普通 GET 查询隐式触发同步。
- 能力列表刷新隐式扫描 COS。
- `sync=true` 绕过 job 机制直接扫描。
- `force=true` 绕过 job 机制直接完整扫描。
- 用阻塞式完整扫描伪装成“刷新当前助手”。
- 用 `asyncio.gather` 或等价方式无上限并发扫描全部助手。

**理由**

同步是有副作用的维护动作，必须具备状态、限流、失败可见性和可恢复性。查询路径必须可预测，不能把用户打开页面变成不可控后台扫描。

**验收口径**

“刷新当前助手”如果没有 `job_id/status`，或接口阻塞等待完整扫描完成，不算通过。

## D3. 一致性承诺是最终一致，不承诺全局实时

**决策**

管理后台展示的是最终一致的索引视图，不承诺全局实时反映 COS 或本地 workspace 的最新内容。

**必须满足**

- 页面必须显示 `last_synced_at`、`sync_status`、`sync_error`、`stale` 或等价时效性字段。
- 同步失败时必须保留旧索引并展示失败状态。
- DB 与 COS 或 workspace 不一致时，页面必须明确这是旧索引或待同步状态。
- 人工绕过系统写入 COS 或 workspace 的内容，只有通过显式 `cos_import` 或 `reconcile` 后才进入默认展示索引。

**明确拒绝**

- 承诺页面全局实时展示 COS 最新内容。
- 承诺页面全局实时展示本地 workspace 最新内容。
- 同步失败后清空列表，让用户误以为文件不存在。
- 不显示 stale/sync 状态却让页面看起来像实时结果。

**理由**

系统无法即时感知所有外部写入、挂载抖动、COS list 抖动和 runtime 侧变化。明确最终一致边界比伪实时更安全，也更容易审计。

**验收口径**

页面没有时效性字段或同步失败会丢失旧索引时，不得标记为 verified。

## D4. 能力安装索引是目标架构必做项，Phase 2 落地

**决策**

助手已安装能力必须有结构化持久索引。该索引是目标架构必做项，不是优化项，也不是可选缓存；落地顺序放在 Phase 2。

**必须满足**

- 索引至少表达助手、能力类型、slug/name、version、enabled、install_path、files_count、source、sync_status、runtime_reload_status、runtime_effective、last_synced_at 和 last_error 或等价字段。
- 能力安装、升级、复用、卸载、启用、禁用成功后，必须更新能力安装索引。
- runtime reload 失败不得回滚已保存索引，但必须标记运行态未生效或 reload failed。
- Phase 2 后，助手已安装能力列表不得默认扫描 COS `skills/plugins` 前缀。

**明确拒绝**

- 长期只靠本地目录位置推断能力是否安装。
- 长期只靠实时 COS scan 推断能力列表。
- 把 runtime 目录加载结果当成后台审计事实源。
- 将能力安装索引降级为可选项。

**理由**

目录推断适合 runtime 加载，不适合作为后台 500-2000 助手规模下的展示索引、审计事实源和权限过滤边界。

**验收口径**

Phase 1 可以不实现能力安装索引，但不得声称“能力安装展示已完成 DB-only 架构”。Phase 2 未完成前，能力安装索引能力不得标记为 verified。

## D5. 缺失、删除、orphan 和 degraded 必须保守处理

**决策**

普通同步只负责补充和更新索引；缺失判断、删除候选和对象清理只能由显式 reconcile 或清理任务处理。

**必须满足**

- `index_only` 同步只 upsert 已发现文件。
- `index_only` 同步扫描不到历史文件时，不得标记最终删除。
- `index_only` 同步扫描不到历史文件时，不得删除对象存储 blob。
- 只有 `reconcile` 可以标记 missing 或删除候选。
- 进入对象清理前，至少需要连续 2 次确认缺失并超过 24 小时保留窗口。
- 对象存储写入成功但 DB 写入失败时，必须记录 orphan object 或 metadata degraded 状态。
- DB 写入成功但对象存储写入失败时，必须保留索引并标记同步失败。

**明确拒绝**

- 页面刷新扫描不到文件就删除 DB 记录。
- 页面刷新扫描不到文件就删除 COS blob。
- 普通同步把临时挂载失败解释为最终删除。
- 未审计、不可追踪的自动对象清理。

**理由**

workspace 临时挂载失败、runtime 重启、COS list 抖动和网络异常都会制造假缺失。删除必须比新增更保守。

**验收口径**

任何普通刷新路径如果能触发最终删除或对象清理，Phase 1 不得通过。

## D6. 技术范围首期保持在现有服务和受限 worker 内

**决策**

首期实现使用现有 Python 服务、数据库、对象存储和受限 worker 模型完成索引查询与同步任务化。

**必须满足**

- 继续使用现有服务边界，不把 IronAgent 特定逻辑扩散到无关模块。
- 同步任务必须持久化到 DB 或等价可靠介质，服务重启后可恢复、可重试或标记失败。
- worker 必须有并发上限、超时、失败重试上限和结构化日志。
- 新增配置继续走现有 Pydantic Settings 风格。
- 日志继续使用现有 structlog 风格。

**明确拒绝**

- Phase 1 引入 Redis。
- Phase 1 引入外部 MQ。
- Phase 1 引入 K8s informer。
- Phase 1 引入 runtime operator。
- Phase 1 引入生产级分布式调度系统。
- 为本 spec 一次性重写 workspace、market、assistant runtime、COS 导入和 UI 全部逻辑。

**理由**

当前第一目标是把页面查询路径从实时扫描中解耦。引入新基础设施会扩大风险、迁移范围和验收成本。

**验收口径**

如果实现依赖新外部基础设施才能满足 Phase 1，则超出本 spec 首期范围。

## D7. 落地顺序必须分 Phase，且不能越级声明完成

**决策**

本 spec 按 Phase 1、Phase 2、Phase 3 小步迁移。各 Phase 可以分 PR 落地，但每个 Phase 的完成声明必须对应行为和证据。

**必须满足**

- Phase 1 必须同时完成：UI 默认不传 `sync=true`、后端 DB-only 分页查询、刷新当前助手 job/status、基础权限过滤、旧索引失败保留、GET 路径零 COS list/零 fan-out/零 workspace scan。
- Phase 2 必须完成：能力安装索引、能力写路径矩阵、能力页默认索引读取、runtime reload 状态分离、能力侧权限验收。
- Phase 3 必须完成：批量任务、COS import、reconcile、backfill、orphan/degraded 修复、删除候选保护和清理审计。

**明确拒绝**

- 只取消前端 `sync=true`，但后端仍 fan-out/COS list，就声明 Phase 1 完成。
- 只新增 job 表，但刷新仍阻塞完整扫描，就声明 Phase 1 完成。
- 能力页仍默认扫 COS，却声明 Phase 2 完成。
- 未完成 reconcile/backfill/orphan 处理，却声明 Phase 3 完成。
- 未提供 `TEST_REPORT.md` 证据就把任一 Phase 标记为 verified。

**理由**

现有工作区文件、能力市场和 runtime reload 链路已有可用基础。分阶段迁移能保留回滚路径，但必须防止“只改表面、不改风险路径”的假完成。

**验收口径**

每个 Phase 必须在 `TEST_REPORT.md` 中列出行为、验证方式和证据；未覆盖的 Phase 只能保持未验收。

## D8. 权限边界必须先于查询复用固化

**决策**

后台全局索引查询和同步任务创建是管理员能力，不能被用户侧或助手侧接口直接复用。新增 DB-only 查询层必须先经过认证主体和可见助手过滤，再访问数据。

**必须满足**

- 后台全局文件 summary 只允许后台管理员会话或内部服务 token。
- 后台单助手文件 summary 必须校验该助手在调用方可见集合内。
- 后台 workspace-items 查询必须校验该助手在调用方可见集合内。
- 单助手刷新 job 必须校验该助手在调用方可见集合内。
- 全量刷新、reconcile、COS import 和删除候选清理必须限制为超级管理员或内部服务能力。
- 用户侧文件查询继续走公开业务 API 的认证和归属过滤，不得调用后台全局索引 API。
- 同步任务创建、失败、取消、reconcile、COS import 和对象清理必须记录审计或系统事件。

**明确拒绝**

- 通过任意 `user_id` 参数复用后台全局索引查询。
- 用户侧或助手侧接口绕过助手可见性过滤。
- 把后台全局 summary 作为公开 API 的通用查询入口。
- 普通管理员无边界触发全量 reconcile 或对象清理。

**理由**

DB-only 查询会提高查询效率，也会放大越权读取风险。权限过滤必须是查询层的前置条件，不是 UI 层的显示约束。

**验收口径**

权限不足时必须返回 401/403 或等价错误，并证明不会泄露其它助手的文件、能力元数据或 job 状态。

## D9. 迁移、回填和回滚必须非阻塞且可重复

**决策**

迁移上线不得要求同步扫描全部对象存储才能打开页面。新增索引、任务表、能力安装索引和约束必须支持可重复迁移、可重入 backfill 和非破坏性回滚。

**必须满足**

- 现有 `workspace_files` 数据继续兼容读取。
- 新增唯一约束前必须完成历史重复数据检查和去重策略。
- backfill 必须可断点续跑，可重复执行，不生成重复索引。
- 能力安装索引缺失时，页面必须能展示 degraded/stale，而不是阻塞打开。
- 关闭 worker 不得影响 DB-only 页面查询。
- 回滚时新增表可以保留不读，不得删除已有 `workspace_files` 数据。
- 迁移失败时只能回滚未完成 migration，不得清理已存在业务文件。

**明确拒绝**

- 上线时阻塞等待全量 COS 扫描完成。
- 迁移脚本不可重复执行。
- 直接添加唯一键而不处理历史重复记录。
- 回滚时删除新增索引表来“恢复干净”。
- 回滚后重新打开页面又默认触发全助手扫描。

**理由**

该改造涉及展示路径、同步任务和索引结构。上线和回滚必须优先保证页面可打开、旧索引可读、同步副作用可停。

**验收口径**

迁移验收必须证明：页面无需全量扫描即可打开；backfill 可重复；关闭 worker 后 GET 查询仍为 DB-only；回滚不破坏已有文件索引。
