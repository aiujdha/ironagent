## 背景

当前管理后台的工作区文件和助手已安装能力展示路径存在实时扫描行为。工作区文件页切换时会触发 `sync=true`，后端对所有助手执行工作区同步；助手已安装能力接口会优先扫描 COS 中 `skills/plugins` 前缀，再从 DB 和本地 workspace 兜底。当前规模下可接受，但后续目标规模为 500-2000 个助手，页面查询路径不能依赖全助手扫描、递归文件系统扫描、实时 COS list 或带副作用的 legacy hydrate。

本 spec 用于固化后续优化方向：管理后台展示以数据库索引为主，扫描和 COS 校验任务化，页面查询保持可分页、可授权、可观测，并保留手动刷新当前助手的时效性入口。

## 摘要

问题：管理后台工作区展示路径把查询、同步、COS 扫描和本地 workspace 读取混在一起，规模扩大后会导致页面慢、接口超时、状态难解释，并可能在临时挂载失败时误标记 missing/deleted。期望结果：后台展示只走纯 DB 索引和分页查询，同步通过显式任务更新索引，页面显示同步状态和时效性。

本 spec 的产品决策是：工作区文件索引化必须从 Phase 1 开始落地；能力安装索引是目标架构必做项，安排到 Phase 2 落地，不再作为可选优化或缓存兜底。Phase 1 的完成口径必须同时包含 UI 不再默认传 `sync=true`、后端 DB-only 分页查询、刷新当前助手返回 job/status 语义，三者缺一不可。

## 问题

- 文件页默认触发全助手同步，助手数量增加后会放大成 `助手数 * bucket * 文件数` 的实时成本。
- 展示路径优先查 COS 摘要，COS 为空或失败才查 DB，容易出现“双数据源不一致”。
- 旧 `WorkspaceFileService.list_files()` 可能触发 legacy COS hydrate，不能直接作为 DB-only 查询。
- 助手已安装能力接口会扫描 COS `skills/plugins` 前缀，虽然有缓存，但 `force=true` 会绕过缓存，且缓存不能解决 500-2000 助手下的总量问题。
- 能力安装态目前主要由目录位置推断，启用/禁用、版本、文件数量、同步状态、runtime reload 状态没有独立稳定索引。
- 全量同步的 `mark_missing` 行为在 workspace 临时不可见时存在误标记 missing/deleted 的风险；另一个 workspace result scan 路径也有缺失即删除记录的行为。
- 页面刷新没有同步任务状态，用户无法区分“数据已刷新”“任务排队中”“同步失败”“展示的是旧索引”。

## 参与方

- 管理员：查看工作区文件、查看能力、刷新当前助手或发起全量校验任务。
- 终端用户：间接依赖后台工作区和能力状态，但不直接触发后台全量同步。
- API 调用方：不得通过弱鉴权参数复用后台全局索引查询；`user_id` 只能作为已授权主体下的过滤条件，不能作为授权依据。
- 助手 runtime：生成 `temp/persistent` 输出，加载 `skills/plugins` 能力目录。
- Workspace：承载助手本地 `temp`、`persistent`、`skills`、`plugins` 目录。
- Skill/plugin：通过市场安装、复用、启用、禁用、卸载到单个助手。
- 内部服务：维护 DB 索引、对象存储元数据、同步任务、审计和权限过滤。

## 生效时机

- 页面查询：发布后立即改为 DB 索引查询，不再默认触发全助手同步、实时 COS list 或 legacy hydrate。
- 单助手刷新：管理员点击“刷新当前助手”后创建同步任务，立即返回 `job_id`、`status` 和当前索引快照；任务完成后该助手索引更新。
- 全量校验：管理员显式触发后后台限流执行，不阻塞页面首次展示。
- 安装/升级/复用/卸载/启用/禁用能力：操作成功后立即更新该助手能力安装索引和必要的文件索引；runtime reload 结果单独记录。
- 文件上传、审批通过写入 workspace、市场安装能力包：写路径必须同步写入 DB 索引。
- Runtime 生成结果文件：首期由受控 scanner/index job 增量写入 DB；不要求本 spec 改造 runtime 输出协议，也不改变 runtime 读取 `skills/plugins` 目录的语义。

## 权限与安全边界

- 只有具备后台管理权限的调用方可以查询全局工作区索引和创建同步任务。
- 后台全局查询、单助手查询、单助手刷新、全量刷新、reconcile、COS import 必须有明确接口鉴权矩阵。
- 用户侧或助手侧查询不得复用后台全局索引接口，也不得直接调用后台全局查询 service 方法后再用 `user_id` 做软过滤。
- 用户侧查询必须从认证主体、绑定关系、可见助手集合推导授权范围；`user_id` 只能在已授权范围内过滤，不能单独决定可见性。
- 页面查询不得绕过统一的助手可见性过滤。
- 同步任务不得因普通 GET 查询隐式触发。
- 全量 reconcile、missing 标记和对象删除必须是显式维护任务，不能由普通页面刷新触发。
- 能力安装、升级、复用、卸载、启用、禁用、同步任务创建、失败、取消、reconcile 和 COS import 必须保留审计或系统事件记录。

## 非目标

- 本 spec 不实现代码；实现前需评审并将状态改为 `ready`。
- 本 spec 不引入 Redis、外部 MQ、K8s informer 或 runtime operator。
- 本 spec 不重做市场 catalog 列表、市场搜索、市场发布流程或市场包来源选择，只调整已安装能力的索引写入和展示读取路径。
- 本 spec 不重写审批 apply 链路；审批通过后的 workspace 写入仍沿用现有 apply 行为，只要求写入成功后补齐索引更新。
- 本 spec 不承诺 COS 或本地 workspace 被人工绕过修改后立即出现在页面。
- 本 spec 不改变公开业务 API 契约，不扩大用户侧文件接口权限，也不把后台全局索引查询暴露给公开 API。
- 本 spec 不改变 runtime 加载 `skills/plugins` 目录的语义，不要求 runtime 为索引化改造能力发现协议。
- 本 spec 不触碰真实环境；首轮实现和验收以本地/测试环境为准。

## 分阶段边界

Phase 1 是最小可交付优化，必须同时满足 B1、B2、B6、B8、B12、B13、B14、B15 和 B20 的对应验收：前端不再默认传 `sync=true`，后端工作区文件 summary/list 是 DB-only 分页查询，刷新当前助手通过 job/status 语义返回，不阻塞页面等待完整扫描。只改 UI 参数、但后端仍可能在 GET 查询中 fan-out、COS list、legacy hydrate 或递归扫描，不能算 Phase 1 完成。

Phase 2 增加能力安装索引和写路径矩阵，覆盖 B3、B4、B5 以及 B15 的能力侧鉴权验收。能力安装索引是目标架构必做项，不是可选项；只是实现顺序排在 Phase 2。Phase 2 之前不得把“继续扫描 COS skills/plugins 但加缓存”解释为目标架构达成。

Phase 3 增加 COS import、reconcile、orphan/degraded 修复、backfill 和清理保护，覆盖 B7、B9、B10、B11、B16、B17、B18、B19。

各 Phase 可以分 PR 落地，但不能把未完成 Phase 的行为标记为 `verified`。

## 行为

B1. 当管理员打开工作区文件页时，系统必须直接查询纯 DB 索引并分页返回；前端不得默认传 `sync=true`，后端也不得因普通 GET 查询触发全助手 workspace 同步、实时 COS list、legacy COS hydrate 或本地 workspace 递归扫描。

B2. 当管理员按助手、bucket、来源类型、同步状态、更新时间筛选工作区文件时，系统必须在 DB 查询层完成过滤、排序和分页，默认 `page_size` 不超过 50，最大 `page_size` 不超过 200；`page_size>200` 必须返回 400，不得静默钳制或先取全量后截断；过滤条件不得退化为先取全量再在内存中过滤。

B3. 当管理员打开助手已安装能力列表或助手详情中的已安装能力时，系统必须优先读取能力安装索引和 `workspace_files` 聚合，不得默认扫描 COS `skills/plugins` 前缀；市场 catalog 列表不属于本行为。

B4. 当能力安装、升级、复用、卸载、启用或禁用成功时，系统必须同步更新该助手的能力安装索引；runtime reload 失败不得回滚索引，但必须标记运行态未生效或 reload 失败。

B5. 当文件上传、审批通过写入 workspace、runtime scanner 发现结果文件或市场安装能力包时，系统必须写入或更新 `workspace_files` 索引；审批写入必须复用现有审批 apply 链路，不得另起不兼容写入路径。

B6. 当管理员点击“刷新当前助手”时，系统必须创建单助手同步任务，立即返回 `job_id`、`status` 和当前索引快照；页面可轮询任务状态，但不得阻塞页面等待完整扫描完成，也不得把刷新动作伪装成同步 GET 查询。

B7. 当管理员点击“刷新全部助手”或“全量校验”时，系统必须创建后台批量任务并限流执行，不得对所有助手无上限并发扫描。

B8. 当同步任务运行时，系统必须记录任务状态：`pending`、`running`、`succeeded`、`failed`、`cancelled` 或等价状态，并记录开始时间、结束时间、范围、扫描数、更新数、错误；重复点击同一 scope 不得创建无限重复 running 任务。

B9. 当普通 `index_only` 同步扫描不到历史文件时，系统不得立即删除对象存储 blob 或把记录标记为最终删除；普通同步只 upsert 已发现文件。只有显式 reconcile 任务才能标记 missing 或进入删除候选。

B10. 当 reconcile 任务发现文件缺失时，系统必须保守处理：至少连续 2 次确认缺失并超过 24 小时保留窗口后，才能从删除候选进入对象清理；清理必须可审计。

B11. 当 COS 中有人工直接写入的文件或能力目录时，页面默认不保证实时显示；管理员必须通过显式 `cos_import` 或 reconcile 任务使其进入 DB 索引。

B12. 当 DB 索引与 COS 或本地 workspace 不一致时，页面必须展示 `last_synced_at`、`sync_status`、`sync_error`、`stale` 或“展示旧索引”提示，不得假装数据实时。

B13. 当同步任务失败时，页面必须保留旧索引并展示失败状态；失败不得导致列表为空或误删既有索引。

B14. 当查询 500-2000 个助手规模的数据时，接口必须支持分页并避免一次返回所有助手的全部文件或能力；Phase 1 的工作区文件 GET 查询 COS list 次数必须为 0、全助手 fan-out 同步次数必须为 0，Phase 2 的已安装能力查询也必须满足同样的无实时扫描口径。

B15. 当执行权限不足的查询或同步任务创建请求时，系统必须拒绝并返回明确错误，不得泄露其它助手的文件或能力元数据；新增 DB 索引查询层不得被用户侧通过任意 `user_id` 参数直接复用，权限判断必须绑定认证主体、角色和助手可见范围。

B16. 当迁移上线时，已有 `workspace_files` 数据必须兼容读取；缺失的能力安装索引可通过可重入 backfill 任务生成，不得要求上线时同步扫描全部对象存储才能打开页面。

B17. 当后台服务重启或同步 worker 重启时，未完成任务必须可恢复、可重试或标记失败，不得永久卡在 running。

B18. 当对象存储写入成功但 DB 写入失败时，系统必须在结构化日志、补偿队列或等价持久介质记录 orphan object 或 metadata degraded 状态，后续校验任务可修复。

B19. 当 DB 写入成功但对象存储写入失败时，系统必须保留索引记录并标记 `sync_status=failed` 或等价状态，页面不得显示为已同步。

B20. 当本 spec 后续实施时，必须先完成小步迁移：Phase 1 同时完成 UI 不传 `sync=true`、后端 DB-only 分页查询和刷新 job/status 语义；只取消前端 `sync=true`、只给旧扫描接口套分页、或后端仍在 GET 路径 fan-out/COS list/legacy hydrate，都不算完成。
